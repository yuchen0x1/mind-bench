# 评分指南

MIND BENCH 使用**三层**评分机制，并在数据层面严格区分"客观可复现"与"主观有噪声"。任何分数都可以追溯到具体规则、裁判模型或评分人。

---

## 一、确定性规则评分（客观）

每题 `scoring_rule` 为独立 JSON，形如 `{"method":"all_keywords","keywords":["甲假","乙真"]}`。由服务端执行，同样输入必然得到同样输出。

| 方法 | 判定逻辑 | 适用场景 | 内置题数 |
| --- | --- | --- | --- |
| `exact` | 归一化（去空白、统一全半角、忽略大小写）后完全相等 | 唯一确定答案、排序结果 | 22 |
| `one_of` | 命中候选集合中任意一个 | 同义表述但可枚举 | 0 |
| `contains` | 回答包含任一关键片段 | 需要提到某概念 | 25 |
| `all_keywords` | 回答包含全部关键词 | 多要点必须齐备 | 84 |
| `any_keywords` | 回答包含任一关键词 | 多解法任选其一 | 0 |
| `numeric` | 解析数值并按容差比较 | 数学计算、估算 | 40 |
| `regex` | 正则匹配 | 严格输出格式 | 2 |
| `json` | JSON 可解析 + 必需键 + 键值约束 | 结构化输出 | 5 |
| `word_limit` | 字数/词数上限 | 简洁性约束 | 0 |
| `manual` | 不自动评分，需人工或 AI 裁判 | 开放式主观题 | 25 |

合计 **178 / 203（87.7%）** 可自动评分，25 题为人工/AI 裁判。

**能力边界（必读）：** 关键词命中**无法**判定上下文否定、语义等价、自相矛盾或论证质量。例如回答"甲不是假的"含"甲"与"假"两个词，但语义与"甲假"相反。因此只有"确实能被字符串/数值客观判定"的题才配置规则评分；这条约束在出题规范中强制执行（见 [测试数据指南](TEST_DATA_GUIDE.md)）。

模型原始回答始终完整保存，评分只从文本中提取字段，**不改写回答**。

## 二、AI 裁判（已实现，辅助手段）

实现于 `src/judge.mjs`，用于开放式回答的结构化辅助评分。它是**辅助**而非真值，所有产出都带来源标注。

### 匿名化

裁判提示词中候选回答被标记为 `Candidate A`，并明确告知裁判"你不知道该回答来自哪个模型"。避免品牌偏好与自我偏袒。裁判模型自身身份不暴露给候选。

### 固定 Rubric

评分维度来自题目 `scoring_dimensions` 字段（内置题默认「任务完成度」「推理与约束遵循」，各权重 1）。裁判**不允许**自行增删维度——多出或缺失维度直接拒绝。

### 严格 JSON + Schema 校验

要求返回：

```json
{
  "dimensions": [
    { "name": "任务完成度", "score": 85, "reason": "..." },
    { "name": "推理与约束遵循", "score": 80, "reason": "..." }
  ],
  "strengths": "...",
  "weaknesses": "..."
}
```

拒绝条件（返回 422，**不是给 0 分**）：

- 自由文本 / 无法解析为 JSON
- 缺少 rubric 中的任一维度
- 出现 rubric 之外的维度
- 分数不在 0—100 区间或非整数
- 标记 `mock: true`

设计原则：**宁可这条运行没有裁判分，也不写入一个可疑的 0 分。** 0 分会被误读为"模型完全失败"，而解析失败只是"裁判没跑通"，两者必须区分。

### 服务端重算总分

不信任裁判自报的 `overall`，由服务端按维度权重重新加权：

```js
const weightSum = dimensions.reduce((s, d) => s + (d.weight || 0), 0) || dimensions.length;
const overall = Math.round(
  dimensions.reduce((s, d) => s + d.score * (d.weight || 1), 0) / weightSum
);
```

### 禁止自评

候选模型 ID 与裁判模型 ID 相同时，请求被拒绝。同一供应商的不同模型可互评，但会被标注。

### 多裁判交叉验证

一次最多选 3 位裁判（`GET /api/judges` 返回候选池，已排除 Mock 与被测模型）。聚合输出：

- `mean`：各裁判总分均值
- `spread`：极差（max - min）
- `agreement`：一致度，`1 - spread/100`

`spread ≥ 25` 时报告页显示"裁判分歧较大"警告，提示人工复核。

### 人工复核优先

`evaluation_results` 中若已有 `evaluator_type='human'` 且 `reviewed=1`，AI 裁判**不会覆盖**，除非请求显式带 `force`。避免自动流程覆盖专家结论。

### 留痕

`judge_verdicts` 表记录：`run_id`、`judge_model_id`、模型版本、原始返回文本、解析后的 JSON、总分、`spread`、`agreement`、时间戳。`UNIQUE(run_id, judge_model_id)` 保证同一裁判对同一运行只有一条（重复为 UPSERT）。

## 三、人工评分

开放式题目可手动打 0—100 分并写评语，写入 `evaluator_type='human'`。适用于创造力、论证质量、科学方案设计、代码可维护性。UI 支持标记 `reviewed`，标记后进入排行榜时优先采信，且不被 AI 裁判覆盖。

正式研究建议预先固定 rubric、双人独立评分并报告一致性（如 Cohen's κ）。当前 UI 只支持单次人工复核，不计算评分者间一致性统计。

## 四、0—100 到 MIND BENCH SCORE

换算链路：

```text
单题分数 (0-100)
  → 按分类聚合为分类均值
  → 按 system_settings.score_weights 的 15 类权重加权平均 (0-100)
  → × 10
  → MIND BENCH SCORE (0-1000)
```

**权重是接入的。** 权重存储于 `system_settings.score_weights`（JSON，15 个键），可在「系统设置」页面直接修改，`buildLeaderboard()` 在每次计算时读取并应用。排行榜响应返回 `weights` 与 `threshold` 字段，报告页会说明本次是否使用了非等权配置——使用者因此能判断分数是否可复现。

**缺测类别的处理：**

- 不作为 0 参与平均（这会系统性惩罚覆盖不全的模型）。
- 只在**已覆盖**的类别上加权，权重和按实际覆盖归一化。
- 同时返回 `category_coverage`（已覆盖 / 15），排行榜显示覆盖度列，提示"分数基于部分能力"。

**0 权重**表示该类别被排除出聚合。

## 五、排行榜准入

只有同时满足以下条件的运行进入正式排名（`qualified`）：

1. 供应商类型非 `mock`；
2. 运行状态为成功；
3. 存在有效评分（规则、AI 裁判或人工，任一）；
4. 回答非空；
5. 该模型在该分类的有效样本数 ≥ `minimum_leaderboard_runs`（默认 10，可在系统设置修改）。

不满足第 5 条但满足 1—4 条的，进入 `provisional` 列表：**单列展示、不占名次、可点击查看模型档案**，并给出原因（如"样本 4/10"）。

**未完成、失败、未评分、Mock 的运行全部被排除在聚合之外，不按 0 分参与平均。**

该阈值是**产品门槛**，用于避免 1—2 次运行就登榜的噪声，不代表统计显著性。

## 六、可复现性清单

发布任何分数时，应同时记录：

- 题库版本（`benchmark_tasks.version` 与快照时间）
- 题目集合（题目 ID 列表或筛选条件）
- 模型 ID 与模型版本
- 采样参数（温度、max_tokens）
- 供应商与调用时间
- 评分方式（`evaluator_type`）及其具体规则/裁判模型版本
- 权重配置快照（排行榜导出的 JSON 已内置）

缺少任一项，跨时间或跨模型的比较就缺乏依据。这也是 `/api/leaderboard/export` 会附带 `weights` 与 `threshold` 的原因。
