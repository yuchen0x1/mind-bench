# 平台可行性与支持边界

评估日期：2026-11-18。产品核心是本地 Node.js 24 + SQLite 服务、浏览器界面和用户自配模型 API；没有原生系统集成、账户认证或公开服务器边界。A/B 表示适合当前产品的开发方向，不表示相应硬件或操作系统已完成实机验收。

| 候选平台 | 级别 | 核心功能、体验与权限 | 构建、分发及更新结论 |
| --- | --- | --- | --- |
| Windows 10/11 浏览器 + 本地服务 | A | 键鼠界面和本地 SQLite 适配；Windows 10 的 Node 24 运行兼容性需实机核对 | 现有压缩包可运行；CI 仅验证 Windows 最新映像，浏览器刷新加载新部署 |
| Linux、Ubuntu、Debian、Fedora、Arch 浏览器 + 本地服务 | A | 同一 Web 核心可用，发行版包管理和文件权限有差异 | Linux CI/Docker 可验证；各发行版尚未实机验收 |
| macOS Intel / Apple Silicon 浏览器 + 本地服务 | B | Node/SQLite 路径理论可行，需两种芯片与系统权限实机验证 | 现有源码/包可尝试；没有 macOS CI、签名、公证或安装器，不标记正式支持 |
| Windows/Linux/macOS 原生桌面应用 | C | 本产品没有托盘、文件拖放、系统通知等必须原生的核心需求 | Electron/Tauri 包装会增加签名、安装器与更新负担；暂不开发 |
| Android 手机、平板与折叠屏浏览器 | B | 已有响应式界面，需真实触控、横竖屏和长时间运行验证；服务需运行在可信本机或受保护网络 | 暂无移动部署/认证边界，不能把 UI 适配等同完整移动产品 |
| iOS / iPadOS 浏览器 | C | 页面可展示，但本地 Node 服务无法作为普通 iOS App 运行；远程服务需先有认证和数据隔离 | App Store 签名、审核与后台限制增加高维护成本 |
| 桌面 Web / 响应式 Web | A | 当前主产品；浏览器与同源 API，数据存于本机 | 已有构建、版本检测、刷新提示和 Release 包 |
| 移动 Web | B | 390px Chromium 已有自动化覆盖；真实手机与可信服务连接待验 | 不发布独立 App；需补充远程访问安全设计后才可跨设备使用 |
| PWA | C | 离线缓存无法执行模型 API 或本地 Node 服务；离线数据恢复语义尚未定义 | Service Worker 可能缓存敏感评测数据并增加更新复杂度 |
| Chrome / Edge / Firefox 扩展 | D | 核心工作流不依赖浏览器页面注入，扩展权限没有明确用户价值 | 商店审核和扩展更新体系会引入额外维护面 |
| Docker / 私有本机部署 | A | 已有镜像、数据卷和健康检查；用户负责保护数据目录与访问边界 | CI 构建并执行容器健康检查；版本升级由镜像替换与备份管理 |
| NAS | B | 具备 Docker/Node 24 的 NAS 可部署，但 CPU 架构、数据卷权限与网络暴露需逐机验证 | 不承诺所有 NAS 型号；沿用容器更新方式 |
| 云服务器 / 公网多用户 | D | 无身份认证、多租户和完整 SSRF 隔离；当前服务不得直接暴露公网 | 需要独立安全架构、迁移与运维方案后重新评估 |
| CLI | C | 可用 HTTP API 自动化，但交互核心仍在 Web | 另造 CLI 的收益不足，先完善 API 文档和脚本示例 |

当前实际交付形态为本机 Web 应用、Node.js 发行包和 Docker 镜像。A/B 候选中尚未完成的设备和系统验收保留为待办，不能作为正式支持声明。
